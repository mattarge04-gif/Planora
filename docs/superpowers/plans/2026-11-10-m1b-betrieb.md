# M1b Betrieb (Paket, Update, Backup/Restore) – Implementation Plan

> **For agentic workers:** Arbeite Task fuer Task, TDD wo sinnvoll, ein Commit pro Task. Checkbox-Syntax (`- [ ]`).

**Goal:** Die M1a-App wird ein installierbares, aktualisierbares und wiederherstellbares Compose-Paket (Spec §3, §7, §8, §9, §14.2–§14.5, §15.2).

**Spec:** `docs/superpowers/specs/2026-11-09-m1-server-paket-design.md` V4 (§15 > §14 > §4–§8). Bei Widerspruch gilt die Spec; Abweichung als [A] im Commit und in `docs/superpowers/plans/m1b-notizen.md` (eigene Spur-Sektion) festhalten.

**Basis:** Branch `m1b-server-paket` (von `main` 4af0a27, M1a enthalten, 98 Tests gruen).

## Global Constraints (beide Spuren)

- Deutsch de-CH in Bezeichnern/Texten, kein Eszett.
- Keine Geheimnisse im Repo. Secrets zur Laufzeit aus `/etc/planora/<instanz>/` (Container: `/run/secrets/...` oder Env-Datei ausserhalb Repo). Test-Secrets pro Lauf zufaellig.
- Images mit **Digest** gepinnt (`image: name:tag@sha256:...`), kein `latest`. npm-Pakete `npm i -E`, Lockfile committen.
- Bestehende M1a-Tests muessen gruen bleiben (`cd app && npm test`).
- Docker: Engine 29.9.3 / Desktop 4.99 auf Windows. Falls `docker` nicht im PATH: `C:\Program Files\Docker\Docker\resources\bin\docker.exe`. Images sind Linux; Shell-Skripte fuer den Host sind POSIX-sh (laufen auf Ubuntu/Debian-Zielhost), Logik bevorzugt in TypeScript (`app/src/betrieb/...`), damit Vitest sie testet.
- **Compose-Projektnamen getrennt:** Spur A `-p planora-a` (Host-Ports 18080/18443), Spur B `-p planora-b` (Host-Ports 28080/28443, DB-Port 25432). Nie `docker system prune`, nie fremde Projekte/Volumes loeschen; nur eigene mit `docker compose -p <eigenes> down -v`.
- Docker-Integrationstests liegen in `app/test-docker/*.test.ts`, eigene Vitest-Config `vitest.docker.config.ts`, Script `npm run test:docker`. Normale `npm test` bleibt ohne Docker.
- Kein Push, kein Merge. Commits deutsch, Ende `Co-Authored-By: ...` (eigenes Modell), nur eigene Pfade `git add <pfad>`.
- Nach 3 Fehlversuchen an derselben Stelle: Task parken (Notiz mit vermutlich falscher Annahme), naechsten Task nehmen.

## Schnittstelle A ↔ B (Vertrag)

- **Backup vor Update (Spec §8 Schritt 3):** A ruft `docker compose -p <p> -f compose.yaml -f compose.backup.yaml run --rm backup sichern --anlass update` auf. Vertrag: Exitcode 0 = Satz `geprueft`; stdout letzte Zeile JSON `{"backupId":"<uuid>","zustand":"geprueft"}`. Exit ≠ 0 = Fehlschlag. A testet mit einem Stub-Service `backup` (eigene Datei `app/test-docker/stub-backup.yaml`), bis B gemerged ist.
- **Letzter gepruefter Satz (§8 Schritt 0):** A liest `select max(start) from backup_lauf where zustand='geprueft'` (Tabelle existiert seit 007).
- **Wartungsflag:** `instanz_einstellung('wartung')` (A legt Semantik in 008 an). B setzt nach Restore Worker/`ki` gesperrt ueber dieses Flag nicht – B setzt Konten `zu_bestaetigen` (§15.2).
- **instanz_id:** `instanz_einstellung('instanz_id')` (seit 001).

## Spur A – Paket & Update (Fable)

### A1 Health + Wartungsflag
- [ ] `008_wartung.sql`: `insert into instanz_einstellung values ('wartung', 'false')` (idempotent `on conflict do nothing`), Funktion `setze_wartung(boolean)` SECURITY DEFINER, EXECUTE fuer `planora_betrieb`; `planora_app` nur SELECT.

- [ ] Tests (embedded-postgres): Health ok, Wartung blockt POST, GET bleibt, DB-Fehler → 503.

### A3 Compose-Paket + Caddy

## Spur B – Backup/Restore (Codex)

### B1 Migration + Betriebsfunktionen
- [ ] `009_backup.sql`: Rolle `planora_migrator` falls fehlt? **Nein** – nur: SECURITY-DEFINER-Funktionen `backup_lauf_start(id)`, `backup_lauf_heartbeat(id)`, `backup_lauf_setze(id, zustand)`, `journal_quittiere(seq)`, `backup_reconcile(container_laeuft boolean)` (§14.3: heartbeat > 10 min und Container nicht laufend → fehlgeschlagen); EXECUTE nur `planora_betrieb`. Tabelle/Spalten fuer Satz-Manifest falls noetig.
- [ ] Tests (embedded-postgres): `planora_app` kann `backup_lauf` nicht schreiben; `planora_betrieb` nur ueber Funktionen; Reconcile-Faelle.

### B2 Sicherungssatz (§7.1, §14.3)
- [ ] `app/src/betrieb/backup/satz.ts`: Lauf registrieren → REPEATABLE READ + `pg_export_snapshot()` → Manifest im Snapshot (Dateischluessel+sha256+groesse, schema/release/modul-Version, instanz_id) → `pg_dump -Fc --snapshot` (Rolle `planora_backup`), `pg_dumpall --roles-only --no-role-passwords` → restic backup (Tag = Backup-ID) → `restic ls`-Abgleich gegen Manifest → `restic check --read-data-subset` → `geprueft`. Exitcode jedes Schritts geprueft. Heartbeat jede Minute. Exporter-Verbindung offen bis pg_dump fertig.
- [ ] Prozessaufrufe hinter Interface (Fake im Unit-Test), echter Lauf im Docker-Test.
- [ ] CLI-Einstieg `sichern --anlass <x>` gemaess Vertrag oben (stdout-JSON, Exitcode).

### B3 Backup-Container + Overlay
- [ ] `betrieb/backup/Dockerfile`: postgres:18 (digest) + restic (gepinnte Version, Checksumme) + node 24 + App-Build (oder Multi-Stage aus `app/`). Kein Docker-Socket.
- [ ] `betrieb/compose.backup.yaml`: Service `backup` (Profile/run-only), Volumes `dokumente` (ro), `backup-staging`, Ziel = restic-Repo. Ziel-Adapter: **Dateisystem/lokales Volume fuer Tests**; S3 (CH-Anbieter) als zweiter Adapter mit derselben Schnittstelle, ungetestet markiert [A] – reale Zieldaten fehlen.
- [ ] Bis A3 da ist: eigene minimale Test-Compose (`app/test-docker/backup-umgebung.yaml`) mit `db` + `backup`, Projekt `planora-b`.

### B4 Journal-Outbox (§7.3, §14.2)
- [ ] `app/src/betrieb/journal/*`: offene Eintraege einzeln, idempotent, mit `age` verschluesselt (Bibliothek oder CLI – Lizenz notieren) als `journal/<instanz_id>/<seq>.age` ans Ziel; nach Erfolg `journal_quittiere(seq)`; jede Minute `stand.age`. Retry, Alarm-Log nach 15 min offen.
- [ ] Tests: Reihenfolge, Idempotenz (doppeltes Senden), Ziel-Fehler → bleibt offen.

### B5 Schluesselinventar (§7.2)
- [ ] Inventar (restic-Passwort, Ziel-Credentials, App-Secrets, DB-Rollen-Passwoerter, instanz_id) age-verschluesselt an Recovery-Key ins Ziel; Test-Recovery-Key pro Lauf erzeugt.

### B6 Restore + Freigabe (§7.4, §14.5, §15.2)
- [ ] `app/src/betrieb/restore/*`: `restore <backup-id> --instanz-id <uuid>`: Inventar entschluesseln → instanz_id pruefen (falsch → Abbruch **vor** Import) → Manifest/Hashes/Release pruefen → Rollen + Dump einspielen → Dateien zurueck + Hash-Abgleich → Journal ab seq lueckenlos nachspielen (Luecke/unlesbar → gesperrt) → alle Sessions/Tokens loeschen → `backup_lauf laufend → fehlgeschlagen` → **alle Konten `zu_bestaetigen`**.
- [ ] `app/src/betrieb/freigabe.ts`: `freigabe` (Host-Konsole): zeigt Benutzer/Rollen/Scope + Journal-Lage, bestaetigt je Admin → Einmal-Token (wie Setup-Token, 15 min), auditiert. Passwort-Reset hebt `zu_bestaetigen` nicht auf (Test).
- [ ] `app/test-docker/backup.test.ts` (A6-Kern): Daten + Datei anlegen → Backup bei parallelem Schreiben → Kontosperre nach Backup (Journal) → `down -v` → frische Umgebung → Restore → Manifest vollstaendig, Sperre wirksam, alle Konten `zu_bestaetigen`, Freigabe → Admin-Login. Negativ: falsche instanz_id, fehlende Datei, fehlendes Inventar, Journal-Luecke → Restore gesperrt.
